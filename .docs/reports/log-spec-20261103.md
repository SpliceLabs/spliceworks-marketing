# Splice Log: spec (2026-11-03)

Status: agreed in conversation, before design. Research digest: `log-competitor-research-20261103.md`.

## Why

- **Readers:** a dated, sourced record of what to do about AI at your stage: what we tested, what we built, what we think, what happened this week. Every claim can be checked.
- **Us:** trust before the call (method on show), a door for every maturity stage, a corpus that earns a newsletter later, and a next step that fits the reader instead of one button everywhere.
- **Why "Log":** entries are dated, coded and statused, with a checked date. That is what separates it from a blog.

## Audience

| Stage | They ask | Lean on |
|---|---|---|
| AI-absent | what is this, what does waiting cost | Guides, Analysis, free tools |
| AI-enabled | how do we make it stick and govern it | Cases, Tools, Guides |
| AI-native | what is proven, what is worth adopting | Tools, Research, Analysis |

Role overlay (hypothesis, founders to check): CEOs and boards lean on Analysis, Cases, Perspective; technology leaders on Tools, Research, Guides; founders on Guides, Tools; accelerators and investors on Analysis, Cases.

## Entry types and page skeletons

Common frame: kicker (Splice Log, code, type, date), title and one-line summary, chips (stage, checked, read time), body by type, Sources, "Ask your AI" box, share bar, related, next step chosen by stage.

- **Launch:** What it does, Who it's for, How to use it, What's new, Questions. A short note announcing something Splice built. Always carries a disclosure that Splice built it; no "How we tested it" and no sources required.
- **Tool:** Overview for third-party tools only (why it is in the log, what we found, what it means for you), Specs, Install and connect, Pricing and limits, How we tested it, Questions, Sources. The Supadata page is the model.
- **Case:** Situation, What we built, Who decides, Result (confirmed only), Disclosure, Next step.
- **Research:** Question, Method, Result, What is still hard, Data or code link.
- **Analysis:** What happened, Our read, What to do next, Sources.
- **Perspective:** The claim, Why, A reasonable counter answered, What we would do.
- **Guide:** Key takeaways, Steps, Questions, Sources, Updated date.

## Frontmatter

```yaml
type: tool | case | research | analysis | perspective | guide | launch
title: ...             # sentence case, no dashes
description: ...       # one sentence, also the card line
published: 2026-11-04  # calendar date
updated: ...           # optional
status: draft | published
stage: absent | enabled | native | all
roles: [ceo, tech, founder, accelerator, investor]   # optional
code: LG-00123         # optional in source; written by the assigner for entries without one
tool_status: added | testing | watching | in-use      # tools
checked: 2026-11-01    # tools and research
sources: [url, ...]    # required for analysis, research, tool, guide
disclosure: ...        # required when a client or maker is affiliated
series: ...            # optional
author: ...            # optional; absent means SpliceOps
hero: { src, alt }     # optional; alt required when src is present
related: [slug, ...]
```

The build fails on a missing required field (for example sources on an analysis, or alt on a hero).

## Reading time (decided 2026-11-03)

- Derived at build time from the entry body, never stored in frontmatter and not overridable.
- Count the words of the body only (front matter excluded, markdown markup and link targets stripped), divide by 250 and round up, shown as "4 min read" (rounding up needs no separate minimum).
- Rounding up overstates by up to a minute; this was chosen deliberately.

## Dates (decided 2026-11-03)

- Shown as D MMM YYYY ("4 Nov 2026"), matching `content/VOICE.md`. Kickers uppercase it. Frontmatter stays ISO (2026-11-04); pages use `<time datetime>` and ISO in structured data.
- The design system's dotted DD.MM.YYYY rule (its README line 35, Ticket and EntryLayout previews) changes in the design system PR.

## Entry codes (decided 2026-11-03)

- Every entry gets a code: `LG-` plus 5 digits, one global sequence across all types.
- The entry's own frontmatter `code` is the record. A person may add one by hand (to seed or reserve a number).
- An assigner script (run by the pre-commit hook and the local build) gives each entry without a code the next number, in order of published date then slug. It never changes an existing code.
- The production build only verifies: a missing or duplicate code fails the build. It never writes, because files written in a CI or Vercel build are not committed and would not persist.
- Existing numbers stay: Supadata 119, Jev 118, and the free tools 120, 121 and 122 become `LG-00119` and so on. The prototype's Jev image checker also used 120 and needs a new number.
- Shown on the entry page kicker, the spec sheet, tool cards and the share image; not in every card's meta line.
- Accepted costs: a backdated entry takes the next number, not a date-ordered one; two branches that add entries in parallel both claim the next number, so the second to merge fails verification and reruns the assigner after deleting its code line.

## Publishing rules

- An entry is live when `status` is published and `published` is today or earlier. Dates are calendar dates compared in UTC.
- `status` is the editorial sign-off; `published` is when it goes live. Both are required to be live: `published` with a future date is approved and scheduled, and a `draft` stays hidden even after its date passes.
- A draft needs only `type`, `title` and `status: draft`. `published` is optional on a draft; every other field is checked only when present, and the full set of rules applies once `status` is `published`.
- A draft gets no `LG-` code until it is published (the assigner skips it), so an abandoned draft burns no number. A draft that already carries a code keeps it and is still checked for duplicates.
- Preview: `LOG_SHOW_DRAFTS=1 pnpm dev` shows drafts and future-dated entries locally, with a `[Draft]` prefix on draft titles. It works only when `NODE_ENV` is exactly `development`; production and test builds ignore it.
- Assets: everything under `public/` is served at its URL whether or not an entry is live (confirmed on a built site), so a draft's files must not sit in `public/log/<slug>/` until it is signed off. Keep them out of the repo's `public/` and add them in the same change that sets `status: published`. A test fails if `public/log/<slug>/` exists for a draft. A signed-off entry with a future date may have its files in place, because it is already approved; only its files are reachable before its date, not the page.
- Merging an entry dated today or earlier deploys it straight away. Backdated entries go live at once but sit in the feed by their date, not at the top.
- Editing a published entry redeploys it and shows the `updated` date.
- A future date is hidden until a daily scheduled run redeploys the site after that date arrives. The run is a GitHub Actions cron that triggers the existing Deploy workflow.

## Hero and share image

- `hero` is optional and feeds three places from one asset: the card, the top of the entry page, and the share image (`og:image` and `twitter:image`).
- No hero means a generated default per entry (type, code and title on the brand wash), so cards and shares always have an image.
- Master size 1200 by 630; cards crop it. Stored at `public/log/<slug>/`.

## Sharing

- Share bar on every entry: LinkedIn, X and Bluesky share links, a native Share icon on phones (this is how Instagram is reached), and a Copy link icon. Copy link is icon-only everywhere, with a tooltip (hover and focus), an aria-label, and a check plus "Copied" after it is pressed. Decided 2026-11-03.
- Public share links only. No API keys, no scripts that post.

## Build

```
content/log/*.md -> schema check (a bad entry fails the build)
  -> getLog() loader (like getPage today; filters to live entries)
  -> /log home, /log/[slug] (template chosen by type), type and stage archives,
     feed.xml, .md copies, llms.txt, llms-full, capabilities.json, sitemap
```

`zod` is not a dependency yet and would be added for the schema. Body text goes through the existing markdown renderer so tables, FAQ and sources use the design system blocks.
